# PROJECT_RULES — постійні правила OVDP Hub

Цей файл є канонічним джерелом постійних правил проєкту. **Будь-яка нова сесія або новий чат починається з `START_HERE.md`**, після чого потрібно прочитати `PROJECT_RULES.md`, `PROJECT_STATE.md` і `WORKLOG.md`.

## 1. Джерела істини

- `START_HERE.md` — обов'язкова перша точка входу для нового чату, нової сесії або відновлення після обриву.
- `PROJECT_RULES.md` — постійні правила.
- `PROJECT_STATE.md` — лише інтегрований стан `main`: checkpoint, версія та наступний великий крок.
- `WORKLOG.md` — оперативний знімок активної роботи: поточний slice, гілка/PR, останній перевірений SHA, блокери й точна наступна дія.
- GitHub Issue #18 `OVDP Hub — live development ledger` — append-only журнал переходів стану активної роботи.
- `apps/native/pubspec.yaml` — машинне джерело номера нативної версії/build.
- `docs/releases/` — незмінні нотатки опублікованих релізів.
- Якщо старий чат або застарілий документ суперечить актуальному `main`, пріоритет має `main`.
- Для незлитої роботи джерелом істини є активна гілка/PR, `WORKLOG.md` у цій гілці та останні записи Issue #18, а не пам'ять чату.

## 2. Активний продукт

- Активний продукт: `apps/native` (Flutter/Dart).
- Цільові платформи: Windows, macOS, Android, iOS.
- Старі TypeScript/Next.js/Expo/Tauri каталоги зберігаються лише як еталон міграції та не є актуальним продуктом.

## 3. Версіювання

Поки продукт має статус 0.x:

- функціональний етап піднімає minor: `0.8.x -> 0.9.0`;
- виправлення, юридичне/пакувальне доопрацювання або сумісна корекція піднімає patch: `0.8.0 -> 0.8.1`;

- уже опублікований Git tag та GitHub Release не пересуваються й не переписуються.

Перехід до `1.0.0` робиться лише за окремим рішенням власника проєкту.

## 11. Команда власника «злити у main», інтеграція і тестові релізи

Щоб не плутати технічний merge з релізною командою власника, використовувати такі терміни:

- **«інтегрувати PR у `main`»** — звичайний технічний merge завершеного slice після зелених checks; сам по собі не означає новий GitHub Release;
- **«злити у `main`» / «зливай у `main`»** — команда власника на **повний тестовий релізний checkpoint для всіх підтримуваних систем**.

Команда **«злити у `main`»** означає повний цикл:

1. завершити поточний функціональний scope і документацію;
2. пройти `flutter pub get --enforce-lockfile`, `flutter analyze`, `flutter test`;
3. підняти версію/build відповідно до правил версіювання;
4. оновити changelog, release notes, PROJECT_STATE/WORKLOG та інші релізні документи;
5. інтегрувати release PR у `main`;
6. виконати release builds/package для **Windows, macOS, Android та iOS**;
7. сформувати також **START/source**, `SHA256SUMS.txt` і legal notices;
8. створити новий незмінний Git tag та опублікувати GitHub **prerelease**;
9. перевірити опубліковані assets і зафіксувати release SHA/run у WORKLOG та Issue #18.

Ритм:

- кожен самодостатній функціональний slice після зелених checks можна **інтегрувати PR у `main`** до початку наступного slice;
- для ручного проміжного тестування можна використовувати START artifact з актуального `main`;
- повне **«злиття у `main`»** з релізами всіх систем планувати регулярно: орієнтир — після **2–3 user-visible integrated slices**, раніше після ризикових parser/calculation/schema змін або негайно за прямою командою власника;
- кожен такий checkpoint отримує нову версію/build; опубліковані tag/release не пересуваються й не переписуються.

## 12. Обов'язковий журнал активної роботи

Щоб розробка не залежала від пам'яті конкретного чату:

1. Перед початком нового slice або після відкриття нового чату прочитати `START_HERE.md`, `PROJECT_RULES.md`, `PROJECT_STATE.md`, `WORKLOG.md` і останні записи Issue #18.
2. До суттєвих змін зафіксувати в `WORKLOG.md`: мету slice, базовий `main` SHA, активну гілку, PR (якщо вже є), критерії готовності та наступну дію.
3. Після кожної зміни стану додати короткий коментар у Issue #18: створено гілку, реалізовано суттєвий блок, пройдено analyze/tests, відкрито PR, CI pass/fail, merge, виявлено blocker.
4. `WORKLOG.md` оновлювати при кожному змістовному checkpoint, а не після кожного повідомлення чату. Він має завжди дозволяти продовжити роботу без цього чату.
5. Статус `DONE` ставити тільки після merge у `main`. Успішний локальний тест або зелений PR до merge — це `VERIFIED`, але ще не `DONE`.
6. Після merge оновити `WORKLOG.md`: записати merge SHA, перенести slice у «Нещодавно завершено», визначити рівно одну наступну активну дію.
7. `PROJECT_STATE.md` оновлювати лише тоді, коли зміна вже інтегрована або суттєво змінює підтверджений стан проєкту.
8. Якщо чат обірвався, не відновлювати роботу з припущень: знайти активний PR/branch, звірити SHA з `WORKLOG.md` та Issue #18 і продовжити з першої незавершеної дії.
