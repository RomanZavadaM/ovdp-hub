# Encrypted vault — dependency / security review

Статус: **PROPOSED FOR APPROVAL — 24.09.2026**  
Governing contract: `docs/security-vault.md`  
Scope: вибір crypto / KDF / device-key stack **до** зміни `pubspec.yaml` і до feature implementation.

## 1. Рішення

Для першої реалізації encrypted vault затверджується така архітектура:

| Concern | Approved stack | Decision |
|---|---|---|
| Vault AEAD | `sodium 4.1.0+1` → libsodium 1.0.22 | **SELECT** `crypto_aead_xchacha20poly1305_ietf` |
| Recovery KDF | той самий libsodium через `sodium` | **SELECT** `crypto_pwhash` з explicit `ARGON2ID13` |
| CSPRNG / DEK / nonce / salt | libsodium `randombytes` + AEAD `keygen` | **SELECT** |
| Android device-key storage | `flutter_secure_storage 11.2.0`, explicit Android options | **SELECT WITH HARDENING** |
| iOS device-key storage | `flutter_secure_storage 11.2.0`, Keychain | **SELECT WITH HARDENING** |
| macOS device-key storage | `flutter_secure_storage 11.2.0`, Data Protection Keychain | **SELECT WITH HARDENING** |
| Windows device-key storage | app-owned adapter over Windows DPAPI via `win32 6.4.0` | **SELECT** |
| Windows `flutter_secure_storage` backend | current DPAPI JSON-file implementation | **DO NOT USE FOR VAULT KEY** |
| Pure-Dart `cryptography 2.9.0` | alternative AEAD/Argon2 implementation | **NOT SELECTED FOR VAULT CORE** |
| Live vault in external provider folder | SAF / security-scoped persistent access | **DEFER FROM FIRST IMPLEMENTATION** |

No dependency is added by this review. The selected versions become implementation inputs only after this document is merged.

## 2. Why libsodium / `sodium`

Reviewed package:
- `sodium 4.1.0+1`;
- package license: BSD-3-Clause;
- bundled upstream libsodium license: ISC;
- supported native Flutter targets include Android, iOS, macOS and Windows;
- `sodium 4.1.0` explicitly updated embedded libsodium to **1.0.22**; `4.1.0+1` refreshed the embedded binaries;
- package minimum Dart SDK: **3.13**.

Upstream libsodium:
- current stable documentation identifies **1.0.22** as latest;
- upstream records a completed third-party security audit;
- the 1.0.22 line includes fixes after the 2025 Ed25519 point-validation issue; that issue is outside the vault's selected XChaCha20/Argon2 path, but it reinforces the policy to reject stale libsodium binaries.

### 2.1. AEAD

Vault v1 uses:

- algorithm id: **`xchacha20poly1305-ietf`**;
- key: **256-bit random DEK** generated by libsodium;
- nonce: **192-bit / 24-byte random nonce** per encryption;
- AAD: the envelope fields required to interpret/decrypt the ciphertext, encoded deterministically;
- encryption/decryption through libsodium only.

Reason:
- libsodium recommends XChaCha20-Poly1305 when interoperability with another library is not required;
- its 192-bit nonce makes random nonces appropriate;
- nonce reuse with the same key remains forbidden;
- AEAD authenticates ciphertext plus AAD and therefore fits the existing fail-closed envelope contract.

The app must expose an app-owned `VaultCrypto` abstraction. Domain/UI code must not call `sodium` directly. This keeps the envelope contract independent from the Dart binding.

## 3. Recovery KDF

Vault v1 recovery wrapper uses:

- algorithm id: **`argon2id13`**;
- libsodium `crypto_pwhash` with **explicit `ALG_ARGON2ID13`** — do not serialize “default” as the format identifier;
- salt: **16 random bytes** (`crypto_pwhash_SALTBYTES`);
- derived wrapping key length: **32 bytes**;
- all KDF parameters (`alg`, `salt`, `opslimit`, `memlimit`) stored in the versioned recovery slot;
- recovery secret is consumed only long enough to derive the KEK and must not be persisted.

### 3.1. Initial parameter profiles

libsodium 1.0.22 defines:

- INTERACTIVE: `opslimit=2`, `memlimit=64 MiB`;
- MODERATE: `opslimit=3`, `memlimit=256 MiB`;
- SENSITIVE: `opslimit=4`, `memlimit=1024 MiB`.

OVDP Hub policy:

1. **portable floor**: never below `opslimit=2 / 64 MiB`;
2. preferred desktop profile: start from **MODERATE (3 / 256 MiB)**;
3. mobile/restricted-memory profile: benchmark MODERATE first; if allocation or measured UX is unacceptable, use **INTERACTIVE (2 / 64 MiB)** and record those exact values in that recovery slot;
4. do not silently reduce an existing slot's parameters during restore;
5. creation UI may offer a stronger profile later, but the first implementation must support both approved profiles;
6. implementation benchmark gate: measure recovery KDF on the project's minimum supported Android/iOS device class plus Windows/macOS CI/dev fixtures and record results before declaring the feature release-ready.

A KDF OOM/error is a hard failure. It must never create a weaker slot automatically.

```yaml
  sdk: '>=3.13.0 <4.0.0'
```

## 5. Android device-key adapter

Selected dependency: **`flutter_secure_storage 11.2.0`**, but defaults are not accepted as-is.

Required vault configuration:

- dedicated `storageNamespace`, e.g. `ovdp_hub_vault_v1`;
- `resetOnError: false` — the package default is `true` and can permanently erase data on an error;
- `migrateOnAlgorithmChange: false` for the vault key store — algorithm migrations must be app-owned and versioned, never implicit;
- `migrateWithBackup: false` for initial vault-key storage;
- explicit key cipher: RSA OAEP SHA-256;
- explicit storage cipher: AES-GCM;
- initial baseline does **not** require biometrics; user-presence may be layered later without changing DEK ownership;
- no fallback from a promised biometric mode into a non-biometric mode without explicit UI state.

Android Auto Backup:
- plugin docs warn that restoring secure-storage SharedPreferences without the device KeyStore key can cause unwrap failure;
- secure-storage artifacts for the vault key must be explicitly excluded from Android backup/device transfer;
- if targeted exclusion cannot be proven in the implementation fixture, set app backup off rather than ship a key-store state that can be restored inconsistently.

The encrypted vault file itself has an independent app-managed backup/recovery path. Secure-storage backup is **not** recovery.

## 6. Apple device-key adapter

Selected dependency: **`flutter_secure_storage 11.2.0`**.

### iOS

Required options:
- `synchronizable: false`;
- `accessibility: KeychainAccessibility.unlocked_this_device`;
- no shared `groupId` for vault key material;
- `useSecureEnclave: false` in the first implementation;
- no iCloud Keychain synchronization.

Apple documents `WhenUnlockedThisDeviceOnly` as available only while the device is unlocked and as **non-migrating to another device**.

Why Secure Enclave is not the v1 baseline:
- the plugin's `useSecureEnclave` mode documents graceful fallback to standard Keychain when the enclave path is unsupported/fails;
- the threat model forbids claiming a stronger property and then silently degrading it;
- baseline security therefore uses explicit device-only Keychain semantics. A later user-presence/Secure-Enclave mode needs its own verified no-silent-downgrade UX.

### macOS

Required options:
- `synchronizable: false`;
- `accessibility: KeychainAccessibility.unlocked_this_device`;
- `usesDataProtectionKeychain: true`;
- no shared access group unless a future approved design requires one;
- `useSecureEnclave: false` initially.

Apple notes that `kSecAttrAccessible` on macOS requires the Data Protection Keychain (or synchronizable keychain); the selected plugin exposes `usesDataProtectionKeychain`, defaulting to true.

## 7. Windows device-key adapter

### 7.1. Rejected path: `flutter_secure_storage_windows` for DEK

The current Windows backend reviewed from upstream:
- stores one encrypted JSON file in application-support storage;
- calls `CryptProtectData` / `CryptUnprotectData`;
- passes no `CRYPTPROTECT_LOCAL_MACHINE` flag, so protection is current-user DPAPI rather than machine-wide;
- **deletes the storage file when DPAPI decrypt or JSON parsing fails**.

That last behavior conflicts with `docs/security-vault.md`:
- corruption/key-loss must enter a clear error/recovery state;
- the app must not silently destroy the only local device-key slot.

Therefore the generic Windows backend is not approved for vault key material.

### 7.2. Approved Windows adapter

Use an app-owned `VaultDeviceKeyStoreWindows` implemented with **`win32 6.4.0`** bindings to the OS DPAPI.

Required behavior:
- `CryptProtectData` / `CryptUnprotectData`;
- **never** set `CRYPTPROTECT_LOCAL_MACHINE`;
- no deprecated prompt flow;
- use `CRYPTPROTECT_UI_FORBIDDEN` for non-interactive operations;
- version the protected-key record;
- optionally pass stable app-specific optional entropy to prevent accidental cross-app decoding; **do not describe that entropy as a secret or an application sandbox**;
- write protected bytes via temp + flush + atomic replace;
- decrypt/format failure leaves the original protected record untouched;
- no auto-delete / auto-reset;
- bind the record to vault id/version and verify after unprotect;
- deletion only on explicit user-approved local-vault removal.

Microsoft documents that DPAPI data is normally decryptable only by the same user credentials and usually on the same computer. Any process already running as that same user can operate within that user's authority; this is consistent with the threat model's explicit exclusion of a fully compromised/unlocked OS. OVDP Hub must **not** claim Windows process isolation from malicious same-user software.

## 8. `win32` package review

Selected Windows binding: **`win32 6.4.0`**.

Reviewed properties:
- current stable as of 24.09.2026;
- BSD-3-Clause;
- Dart SDK minimum 3.10;
- exposes Win32 APIs directly through FFI;
- v6.x uses explicit result/error handling suitable for checking DPAPI failures.

It is an API binding, not a cryptographic implementation. The cryptographic primitive remains Windows DPAPI.

## 9. Alternative reviewed: `cryptography 2.9.0`

Positive:
- Apache-2.0;
- cross-platform;
- provides XChaCha20-Poly1305 and Argon2id;
- lower Dart SDK floor;
- `cryptography_flutter` can delegate some algorithms to OS implementations on Android/iOS/macOS.

Reason not selected for vault core:
- XChaCha20 and Argon2id have pure-Dart implementations in the package;
- the Flutter companion may fall back to background/pure-Dart implementations when platform algorithms are unavailable;
- this review found extensive tests and active maintenance, but did **not** find evidence of an independent third-party audit comparable to libsodium's recorded audit.

This is **not** a statement that `cryptography` is insecure. It is a dependency-evidence decision: for a financial vault, libsodium better satisfies the approved “audited standard primitive implementation” bar with less implementation-specific crypto surface owned by this project.

## 10. Dependency and advisory policy

Initial implementation must use exact direct constraints:

```yaml
sodium: 4.1.0+1
flutter_secure_storage: 11.2.0
win32: 6.4.0
```

and keep `pubspec.lock` committed/enforced.

Security-critical dependency upgrades are **not** bundled into unrelated feature work. Each upgrade requires:
1. upstream changelog;
2. package + upstream native version check;
3. advisory review;
4. Windows/macOS/iOS/Android build/test run;
5. envelope compatibility check;
6. update of third-party license/notice documentation.

Advisory note at this review date:
- no package-specific GitHub advisory surfaced in this review for `sodium`, `flutter_secure_storage` or `win32`; absence of a surfaced advisory is not proof that none exists;
- upstream libsodium had the 2025 Ed25519 point-validation issue affecting particular Ed25519 validation uses; reviewed libsodium 1.0.22 is after that fix and the selected vault primitives are XChaCha20-Poly1305 + Argon2id, not that Ed25519 validation path.

## 11. External vault location

The first implementation must **not** make a cloud/provider document URI the live mutable vault.

Approved v1:
- active vault lives in app-managed local storage;
- user can create an explicit **encrypted portable backup** to a user-selected location;
- existing file-picker/export mechanisms may be used for explicit backup import/export if they do not persist plaintext secrets.

Deferred:
- live vault directly inside Android SAF provider / iOS or macOS security-scoped provider path;
- multi-device synchronized mutation.

Reason: persistent URI/bookmark renewal, provider atomic-write semantics and ciphertext conflict resolution are separate risks. They should not block local encrypted-vault delivery or weaken atomicity.

## 13. Implementation gates

The first code PR is blocked until it satisfies all gates below.

### Build / compatibility
- raise Dart floor to >=3.13.0;
- update `pubspec.lock`;
- update license/third-party notice material for sodium/libsodium, flutter_secure_storage and win32;
- Windows, macOS, iOS and Android builds must all resolve native assets/plugins.

### Crypto
- `sodium` initialization failure = vault unavailable, never plaintext fallback;
- XChaCha20-Poly1305-IETF only for vault v1;
- random DEK and nonce generated by libsodium;
- nonce size asserted from library API;
- AAD deterministic and authenticated;
- unknown algorithm id/version fails closed;
- `SecureKey` disposed as soon as practical; no guarantee of complete Dart heap zeroization is claimed.

### Recovery
- explicit Argon2id13;
- only approved 2/64 MiB or 3/256 MiB profiles;
- exact KDF values serialized per recovery slot;
- OOM/time failure never downgrades automatically;
- benchmark evidence recorded before release-ready status.

### Device key
- Android: dedicated namespace, `resetOnError=false`, migration disabled, backup exclusion verified;
- iOS: non-sync + `unlocked_this_device`;
- macOS: same + Data Protection Keychain;
- Windows: DPAPI current-user, UI-forbidden, non-destructive error handling;
- missing/corrupt protected key produces recovery/error state, never new-key auto-generation over an existing vault.

### Regression
- wrong key/corrupt ciphertext fails authentication;
- AAD modification fails;
- Windows DPAPI corruption test leaves source record intact;
- Android secure-storage error does not reset key;
- Apple device-only item configuration verified in integration test;
- fresh-profile recovery works without device key;
- lower known revision produces rollback warning;
- interrupted vault write preserves prior known-good file;
- release/source artifact scan contains no fixture DEK/recovery secret/private vault.

## 14. Explicit non-decisions

This review does not yet choose:
- biometric/user-presence UX defaults;
- auto-lock timeout values;
- record-level synced-device conflict merge;
- Secure Enclave mode;
- live SAF/security-scoped vault;
- exact payload record schema beyond the threat-model invariants.

Those are not needed to start the crypto/storage foundation after this review is merged.
