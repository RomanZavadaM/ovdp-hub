# PROJECT_RULES — постійні правила OVDP Hub

Цей файл є канонічним джерелом постійних правил проєкту. Перед змінами в OVDP Hub потрібно читати його разом із `PROJECT_STATE.md`.

## 1. Джерела істини

- `PROJECT_RULES.md` — постійні правила.
- `PROJECT_STATE.md` — поточний checkpoint, версія та наступний крок.
- `apps/native/pubspec.yaml` — машинне джерело номера нативної версії/build.
- `docs/releases/` — незмінні нотатки опублікованих релізів.
- Якщо старий чат або застарілий документ суперечить цим джерелам, пріоритет мають актуальні файли в `main`.

## 2. Активний продукт

- Активний продукт: `apps/native` (Flutter/Dart).
- Цільові платформи: Windows, macOS, Android, iOS.
- Старі TypeScript/Next.js/Expo/Tauri каталоги зберігаються лише як еталон міграції та не є актуальним продуктом.
- Web/PWA не входить до поточного продукту.

## 3. Версіювання

Поки продукт має статус 0.x:

- функціональний етап піднімає minor: `0.8.x -> 0.9.0`;
- виправлення, юридичне/пакувальне доопрацювання або сумісна корекція піднімає patch: `0.8.0 -> 0.8.1`;
- Flutter build number після кожного опублікованого checkpoint збільшується і не перевикористовується;
- уже опублікований Git tag та GitHub Release не пересуваються й не переписуються.

Перехід до `1.0.0` робиться лише за окремим рішенням власника проєкту.

## 4. План, дані та приватність

- OVDP Hub є інформаційним та планувальним інструментом, а не брокером.
- Не реалізовувати торгівлю, KYC, централізовані портфелі або збір приватних інвестиційних даних без окремого рішення власника.
- Розрахунки та приватні сценарії залишаються на пристрої.
- Не додавати аналітику, session replay, remote fonts чи сторонні скрипти стеження.
- Публічні ринкові дані не можна подавати як гарантовано актуальні або виконувані котирування без відповідного підтвердження джерела.

## 5. Фінансові розрахунки

- Грошові значення зберігаються і рахуються через Decimal.
- Double дозволений лише для представлення та окремо протестованого чисельного XIRR solver.
- Невідома комісія не підміняється нулем мовчки.
- Синтетичні приклади мають бути явно позначені.
- Результати планувальника не можна називати інвестиційною рекомендацією.

## 7. Перед merge

Для змін у активному Flutter-коді обов'язково:

1. `flutter pub get --enforce-lockfile`;
2. `flutter analyze`;
3. `flutter test`;
4. для релізного checkpoint — release build відповідних платформ;
5. перевірити, що робочі папки, портфелі, ключі, БД та персональні файли не потрапили до Git.

## 8. Реліз

Кожний GitHub Release повинен мати:

- унікальний tag `vX.Y.Z`;
- release notes у `docs/releases/RELEASE_NOTES_vX_Y_Z.md`;
- START/source пакет;
- доступні платформні тестові пакети;
- `SHA256SUMS.txt`;
- legal notices;
- чітке маркування signing-статусу та обмежень тестової збірки.

Для 0.x релізи за замовчуванням публікуються як **prerelease**, доки власник не визначить стабільну виробничу лінію.

## 9. Захист main

- Роботу бажано вести через окрему гілку + PR.
- Merge робити після успішних checks.
- Для публічного репозиторію GitHub ruleset/branch protection має вимагати PR та успішні checks, коли адміністративні налаштування доступні.
- Відсутність технічного ruleset не скасовує ці правила розробки.
